# Brutal Fist — Move / Animation Architecture

## Goal

Every playable Bannon fighter should be able to use a large, data-driven moveset assembled from verified animation sources instead of requiring a brand-new animation for every attack, transition, locomotion state, grapple, reaction, or wake-up.

## Authority

1. Bannon owns the playable fighter content and Bannon-authored animation assets available to this project.
2. Schwarzerblitz remains the native runtime authority.
3. Open-source/research projects are architectural sources; their code and data are adapted only where their license/permission permits.
4. External game animation files are imported only when the project has the necessary rights to use those files. Researching a game's architecture does not by itself grant rights to redistribute its animation assets.
5. No procedural animation fallback may silently replace a missing real animation.

## Animation pipeline

`source asset -> inventory -> semantic classification -> rig compatibility -> retarget -> measured QA -> gameplay binding -> fighter moveset`

The inventory must include real Bannon FBX/GLB assets under the BannonSource tree. Metadata-only entries remain metadata-only until a real asset is present.

## Move sharing

A move definition is independent from a fighter identity. The same verified animation can be bound to multiple fighters, while frame data, damage, cancel rules, movement, hitboxes, and presentation can vary by moveset slot when the game design calls for it.

This supports mixed movesets such as:

- boxer-style hands + wrestling grapples
- kick-heavy striking + Bannon throws
- fast locomotion + heavyweight knockdowns
- character-specific signature sequences assembled from existing verified clips

## Fighter customization

Move customization is the first customization layer. A fighter gets a `FighterMoveSet` containing named slots and move IDs. Personality/bio-driven tags must come from authoritative Bannon data; the system must not invent personality traits and use them as facts.

Later customization can add independent appearance layers for colors, hair, clothing, and attire without changing the fighter's canonical identity or GLB gate.

## Required gates

- real asset exists
- asset is readable and non-truncated
- skeleton/rig is compatible or successfully retargeted
- clip is measurable
- no NaN/Inf transforms
- bind/rest pose is valid
- animation does not violate root-motion bounds
- gameplay frame data exists before competitive use
- `UNKNOWN` is never `PASS`
- missing animation locks that slot rather than substituting a generated actor/clip

## Source strategy

Schwarzerblitz, Bannon, the Grok architecture lineage, and the supplied fighting-game research repositories can contribute architecture behind the BF contracts. The implementation should consolidate their strongest deterministic timing, frame-data, state-machine, collision, resource, animation-lifecycle, and camera patterns rather than concatenate independent runtimes.

The Bannon animation inventory is generated by `npm run bannon:manifest` and is intentionally exhaustive over the configured Bannon asset roots.
